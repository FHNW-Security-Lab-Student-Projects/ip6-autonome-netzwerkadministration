# A2A Task ID and Context ID Lifecycle

How `task_id` and `context_id` are generated, who decides their values, and how they enable multi-turn conversations in the A2A protocol.

## The Two Identifiers

### `task_id` — identifies a single task

A task is a single, stateful operation between client and agent. It has a status lifecycle (`submitted` → `working` → `completed` / `input-required` / `failed`), a message history, and artifacts.

> *"A unique identifier for the task, generated by the server for a new task."*
> — `Task.id` in `a2a-python/src/a2a/types.py`

### `context_id` — groups related tasks into a session

A context groups multiple related tasks together. Think of it as a session ID — task 1 might tell a joke, task 2 might translate it, both sharing the same `context_id`.

> *"A server-generated unique identifier (e.g. UUID) for maintaining context across multiple related tasks or interactions."*
> — `Task.context_id` in `a2a-python/src/a2a/types.py`

## Who Decides the ID Values?

Both `task_id` and `context_id` follow a **"suggest or auto-generate"** model. The logic lives in `RequestContext` (`a2a-python/src/a2a/server/agent_execution/context.py`).

### Decision Flow for `context_id`

The method `_check_or_generate_context_id()` (context.py:185-197):

```python
if not self._context_id and not self._params.message.context_id:
    # Neither server nor client provided one → generate a new UUID
    self._params.message.context_id = self._context_id_generator.generate(...)
if self._params.message.context_id:
    self._context_id = self._params.message.context_id
```

| Scenario | What happens |
|---|---|
| Client sends a `context_id` | Server accepts and uses it |
| Client sends no `context_id` | Server auto-generates a UUID |
| Client sends `context_id` that mismatches an existing task | Server raises `InvalidParamsError` (context.py:76-78) |

### Decision Flow for `task_id`

The method `_check_or_generate_task_id()` (context.py:173-183) works identically:

| Scenario | What happens |
|---|---|
| Client sends a `task_id` | Server looks it up; if found, continues it |
| Client sends no `task_id` | Server auto-generates a UUID for a new task |
| Client sends a `task_id` that doesn't exist | Server raises `TaskNotFoundError` (default_request_handler.py:228-232) |

### Summary

```
Client                              Server (RequestContext)
  │                                       │
  │  Message(context_id=None,             │
  │          task_id=None)                │
  │ ────────────────────────────────────► │  generates both IDs via UUIDGenerator
  │                                       │
  │  Task(id="abc", context_id="xyz")     │
  │ ◄──────────────────────────────────── │  returns server-generated IDs
  │                                       │
  │  Message(context_id="xyz",            │
  │          task_id="abc")               │
  │ ────────────────────────────────────► │  validates & continues existing task
  │                                       │
  │  Message(context_id="xyz",            │
  │          task_id=None)                │
  │ ────────────────────────────────────► │  new task, same session (context)
```

In practice:
- **The client decides when to start a new context** (by sending a new `context_id` or omitting it).
- **The server decides the canonical value** and enforces consistency on follow-up messages.

## `contextId` Is a Metadata Label, Not a Retrieval Key

A common misconception is that the server uses `context_id` to retrieve all tasks belonging to a conversation. **It does not.** The `contextId` is stored on each task, but there is no mechanism in the SDK to query tasks by it.

### What `TaskStore` actually provides

```python
class TaskStore(ABC):
    async def save(self, task, context) -> None
    async def get(self, task_id, context) -> Task | None   # by task_id only
    async def delete(self, task_id, context) -> None        # by task_id only
```

No `get_by_context_id()`. No `list_tasks()`. No `search()`.

### How context retrieval actually works

The server has **two** ways to access conversational history, and neither uses `context_id`:

| Mechanism | How it works | Who drives it |
|---|---|---|
| **Same `task_id`** | Client sends follow-up messages with the same `task_id`. The task accumulates messages in its `history: list[Message]` field. | Client (reuses `task_id` from response) |
| **`reference_task_ids`** | Client explicitly lists other task IDs in `message.reference_task_ids`. The server's `SimpleRequestContextBuilder` (if configured with `should_populate_referred_tasks=True`) fetches each referenced task and passes them as `related_tasks` to the `AgentExecutor`. | Client (provides the IDs) |

### So what is `contextId` for?

It's a **grouping label** — metadata that tags tasks as belonging to the same session. It enables:

- **Consistency validation**: The server rejects messages where `context_id` doesn't match the existing task's `context_id` (context.py:74-78).
- **Custom extensions**: A developer could subclass `TaskStore` to add a `get_by_context_id()` method (the `DatabaseTaskStore` already indexes `context_id` as a column). But this is outside the SDK's built-in behavior.
- **Observability / debugging**: Knowing which tasks belong together is useful for logging and tracing.

### Key takeaway

> **Building conversational context across tasks is the client's responsibility.** The client must track which `task_id`s belong to a conversation and pass the relevant ones via `reference_task_ids`. The server cannot reconstruct a conversation from `context_id` alone.

For the full analysis of context retrieval responsibility, see [a2a-message-context-responsibility.md](a2a-message-context-responsibility.md).

## Multi-Turn Conversations (`input-required`)

When a server agent needs clarification, it sets the task state to `input-required` via `TaskUpdater.requires_input()`. The client must then send a follow-up message with both `task_id` and `context_id` to continue the same task.

### Server Side (AgentExecutor)

```python
# In your AgentExecutor.execute():
if output.needs_input:
    await updater.requires_input(
        message=new_agent_text_message("Could you clarify the topic?"),
        final=True,
    )
```

`TaskUpdater.requires_input()` sets `TaskState.input_required` and publishes the status update. The `final=True` parameter signals that the event stream for this turn is done — the client should now respond.

### Client Side

```python
# After receiving the response, check if the server needs more input:
if task.status.state == TaskState.input_required:
    # Prompt user, then send follow-up with same task_id + context_id
    follow_up = Message(
        role='user',
        parts=[Part(root=TextPart(text=user_reply))],
        message_id=uuid4().hex,
        task_id=task.id,          # continue THIS task
        context_id=task.context_id,  # stay in THIS session
    )
    async for event in client.send_message(follow_up):
        ...
```

### What Happens on the Server

When the follow-up message arrives with a `task_id` (default_request_handler.py:210-233):

1. `TaskManager` is created with `task_id` and `context_id` from the message
2. The existing task is fetched from the `TaskStore`
3. The new message is appended via `task_manager.update_with_message()`
4. `AgentExecutor.execute()` is called again with the updated context

## When to Reset vs. Reuse

| Action | `task_id` | `context_id` |
|---|---|---|
| Continue after `input-required` | Same (reuse from response) | Same (reuse from response) |
| Start a new task in the same session | `None` (let server generate) | Same (reuse from response) |
| Start a completely new session | `None` | `None` (or generate a new one) |
