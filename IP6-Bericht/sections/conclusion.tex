\section{Conclusion and Future Work}
\label{sec:conclusion}

This section answers the five research questions of
\Cref{sec:research-questions} in short form and states what the project does and does not show.
\Cref{sec:future-work} then collects the open points that follow from this work. 

\subsection{Conclusion}
\label{sec:conclusion-summary}

This project built an AI-driven multi-agent system that troubleshoots network problems by
splitting and delegating work to specialised sub-agents. This system was used to
run 300 experiments. The experiments consisted of a healthy baseline plus nine fault scenarios across
three difficulty tiers, using six models from three price tiers, with five runs each. Every run was scored manually against the known root cause.
With respect to the research questions from \Cref{sec:research-questions}, the experiment
supports the following answers (within the limitations mentioned in \Cref{sec:eval-limitations}).

\begin{enumerate}
    \item \textbf{Time}: With certain models the system delivers a correct result in two to
          four-and-a-half minutes. Compared to an
          estimated 10 minutes to 2 hours of manual work depending on the tier, the saving is
          small for trivial faults but can be large for more difficult problems. The comparison rests on an
          estimated manual troubleshooting time. No human trials were done.
    \item \textbf{Difficulty}: Every difficulty tier was solvable, but only the
          high-tier models solved every tier reliably. Mid-tier models handled the easy tier reliably but
          failed mostly on two scenarios, the medium-tier \texttt{duplicate-ip-arp} and the hard-tier
          \texttt{acl-silent-drop}, by hitting the time cap without a result rather than
          concluding wrongly. The manually assigned tiers predicted model behaviour only partially.
    \item \textbf{Success rate}: GPT-5.5 diagnosed 50/50 runs correctly and Claude Opus 4.8
          48/50. The mid tier reached 74--82\,\% overall (near-perfect on easy, about 70\,\%
          on medium and hard combined). The low tier models were unusable at 16--22\,\%.
    \item \textbf{Cost}: A complete investigation costs \$0.01--\$2.91 in API
          fees per run depending on the model, or \$0.07--\$2.91 per correct diagnosis
          (\$0.21--\$2.91 for the mid- and high-tier models that are actually usable). Against an
          example rate of CHF 100 per network operator hour, a correct automated diagnosis of a medium or
          hard fault costs a fraction of the manual equivalent.
    \item \textbf{Model influence}: The model is the deciding factor.
          With the same agent logic, success ranges from 16\,\% to 100\,\% depending only on which
          model is used, while the API fee per correct diagnosis spans \$0.21--\$2.91 across the
          usable models.
\end{enumerate}

Beyond the measured experiments, the project's second part, the automatic syslog
investigation (\Cref{sec:autonomous-syslog-usecase}), proved feasible. During development the
system reacted to real syslog events without any human trigger, opened self-contained
investigations, produced initial triage reports and persisted them so that an operator can
take over the case later without repeating the completed work
(\Cref{sec:impl-investigations}). This part was validated qualitatively and was deliberately
not part of the quantitative evaluation.

Using a multi-agent system for network troubleshooting is technically feasible today. With a
high-tier model, root-cause detection was very good in this lab. Whether this holds up in a
production network, with more devices, more alarms and multiple faults, remains open.

\subsection{Future Work}
\label{sec:future-work}

The weakest assumption in this evaluation is the estimated manual baseline. A study in which
network operators troubleshoot the same faults would replace it with measured
data. The same work could also cover an interactive use case of the agent system, where network operators and agents are working
together instead of the fully autonomous single-prompt mode measured here. Future evaluations
should also use a larger environment: more devices, mixed vendors, several concurrent faults,
background noise in syslog, and scenarios where the root cause of the problem lies outside the network (DNS, host
configuration).

A second thing is the harness itself. The experiments varied the model while the harness
stayed fixed, but the harness is a system of its own. One technique that was not applied in this
work is \emph{agent skills}. They package instructions and reference material that an agent
discovers through a name and a short description, whose full content is loaded into the
context only when the task requires it. This is a principle called \emph{progressive
disclosure} \parencite{anthropic_agent_skills}. Further harness-side improvements are explicit prompt caching (for models which allow client side steering), which would
lower the real API cost per run (the cost metric of \Cref{sec:metrics} deliberately prices
uncached tokens). Additionally a finer history compaction that summarises older tool returns instead of
replacing them entirely (\Cref{sec:impl-context}).

Three further experiments follow directly from the findings. The first is a check of the
architecture itself. The multi-agent design was never compared against a single agent holding
all tools in one context. Running the matrix with such a flattened variant would show whether
the decomposition of \Cref{sec:architecture} contributes to the success rate or whether the
model would perform equally well without it. 

The second is a sensitivity analysis of the wall-clock cap. 
The mid-tier models failed mostly by hitting the 600-second cap without a
result (\Cref{sec:eval-limitations}), so their measured success rate depends partly on where
the cap sits. Repeating the failed combinations with a higher cap would show better where the limits of these models are.

The third is mixed-model configurations. In the
experiments the same model was used across all agents (\Cref{sec:experiments}), although the
sub-agents work on narrower tasks than the orchestrator. A configuration with a high-tier
orchestrator and cheaper sub-agent models was not tested.

The last point is the scenario catalogue stopping at the hard tier. The originally planned fourth tier, faults that
are only visible by comparing the current state against a recorded working state (not visible in syslog and not visible using show commands) via state-snapshot agent
(\Cref{sec:scenario-descriptions}), was never realised, because the intended use-case turned out
to be solvable via syslog (visible in syslog). No scenario in the final catalogue therefore forces the
state-snapshot agent (\Cref{sec:agent-roles}) to be used. A new scenario that does not appear in the syslog and cannot be seen using the device show commands would need to be constructed.
