\section{Concepts}
\label{sec:concepts}
While \cref{sec:background} introduced the underlying technologies in general terms, the
concepts section explains how they are applied to the problem of network troubleshooting and why the
multi-agent troubleshooting system is designed the way it is. The realisation (implementation) in code is deferred to
\cref{sec:implementation}, and the experimental procedure used to evaluate the design is described in
\cref{sec:methodology}.


\subsection{Scope: Two Independent Parts}
\label{sec:concepts-scope}
The work described in this report consists of two distinct and largely independent parts, which it is
important to keep apart conceptually.

The first part is the core of the project and addresses the research questions stated in
\cref{sec:introduction}, which network problems can be troubleshot by a multi-agent system, with what
success rate across difficulty levels and at what cost. This part is driven by a human operator who poses a
troubleshooting goal to the orchestrator agent and it is evaluated against multiple fault scenarios (see \cref{sec:evaluation-concept,sec:model-tier-concept}).

The second part is an independent feasibility use case rather than a measured research question, the
\emph{automatic syslog investigation}. The question here is simply whether it is possible to build a system that reacts
autonomously to certain syslog messages and starts a self-contained initial investigation without any
human trigger. A second question is how such
a mechanism works in practice and how a human operator can take over and continue the troubleshooting without
repeating the work the autonomous investigation has already done. This use case reuses the same
agent building blocks shown in \cref{fig:architecture-overview} but uses a different entry point (\texttt{investigation\_orchestrator}). It is described on its own in
\cref{sec:autonomous-syslog-usecase} and is not part of the quantitative evaluation.

\subsection{Overall Architecture}
\label{sec:architecture}
The system is structured as a \emph{hierarchical}, \emph{role-based} multi-agent system, the collaboration
pattern introduced in \cref{sec:multi-agent}. The \emph{orchestrator} agent receives a troubleshooting
goal and delegates sub-tasks to specialised sub-agents, each responsible for a specific task or domain (see \cref{sec:agent-roles}).

The main reason for distributing the work across several agents instead of using one monolithic
agent comes from the limitations discussed in \cref{sec:tokens-context-cost}. A single
agent would have to hold the entire troubleshooting context (all tool definitions, all device output, the full
conversation history) in one large context window. This approach risks hitting the context limit quickly and
thereby degrading output quality through the \enquote{lost in the middle} effect (introduced in \cref{sec:tokens-context-cost}). In comparison, when using multiple specialised agents, they receive
only focused instructions and tools, which keeps the individual contexts small and reduces context-related quality degradation.

Each LLM-driven agent (AI agent) in this architecture is an independent agent loop (see \cref{sec:agent-loop}). It runs its own
loop over its own context and tools, using the same underlying agent harness. (The topology agent is the one
exception, \cref{sec:impl-delegation} explains why it is not LLM-driven.) Delegation is itself realised as a
tool call. The orchestrator's loop invokes a sub-agent as a tool, the sub-agent runs its own loop to completion and
returns its result, which the orchestrator then incorporates into its own context.

\Cref{fig:architecture-overview} shows the resulting architecture, the orchestrator at the top delegates
sub-tasks to the specialised sub-agents, each of which has its own tools.

\subsection{Agent Roles and Responsibilities}
\label{sec:agent-roles}
Each agent has one responsibility and a fixed, narrow scope. The following roles make
up the system:

\begin{itemize}
    \item \textbf{Orchestrator (user-facing)}: Receives user input and coordinates the sub-agents. It splits
          the user's goal (task) into sub-tasks and delegates them to the sub-agents and combines their results into a final answer. Since the sub-agents are \enquote{stateless} the orchestrator
          needs to supply all the required information to the sub-agents.
    \item \textbf{Investigation orchestrator (autonomous)}: Coordinates the autonomous syslog-event-based investigations.
          It runs the same delegation pattern as the user-facing
          orchestrator without access to the configuration agent.
    \item \textbf{Network agent}: Retrieves live device state through read commands.
    \item \textbf{State-snapshot agent}: Provides historical device state. The state-snapshot agent focuses on information which cannot be retrieved via syslog or
          device live state but can be useful for troubleshooting (like past ARP entries or routing tables).
    \item \textbf{Topology agent}: Supplies the (cached) network topology so other agents can reason about how
          devices are connected. It compares the \enquote{should be} state of the topology with the actual \enquote{live} state of the network (via LLDP queries).
    \item \textbf{Syslog agent}: Queries and analyses syslog data for the entire network.
    \item \textbf{Configuration agent}: The only agent with \emph{write} access. It is able to apply
          configuration changes to devices.
\end{itemize}

\subsection{Tool and Capability Layer}
\label{sec:tool-layer}
Agents gain the ability to interact with the outside environment through the function-calling mechanism described in
\cref{sec:func-calling}, exposed via the Model Context Protocol introduced in \cref{sec:mcp}. Most
agents are served by their own MCP server, so every agent only gets the tools that are required
for its specific task.

This split of expertise is a design choice that supports the architecture of
\cref{sec:architecture}. It keeps every agent's tool definitions, and therefore its context, small and precise.

Not every agent follows this pattern. Two agents, the topology agent and the state-snapshot agent,
do not use MCP servers. Their tools are defined directly inside the agent framework as native
function tools, because both read state that a background task inside the same process already
collects and caches (topology and device state). Sending such calls through an MCP server would
add a process boundary and serialisation overhead without any of the benefits described in
\cref{sec:mcp}. The topology agent goes one step further. As \cref{sec:impl-delegation} describes,
it has no model and no agent loop at all. The state-snapshot agent is a
regular Pydantic AI agent. Only its tools are in-process.

\subsection{Model-Tier Concept}
\label{sec:model-tier-concept}
LLMs can be compared to each other using a variety of metrics. This work uses the \emph{price per million tokens} as the comparison metric, because cost is a primary research question.
Models are grouped into \emph{tiers} according to their \emph{price} (low, mid and high). The system is
designed so that the model tier can be changed independently of the agent logic, which makes it possible to
study how model choice affects the success rate and cost in terms of troubleshooting networking issues.
The concrete models assigned to each tier are described in \cref{sec:methodology}.

\subsection{Evaluation Concept}
\label{sec:evaluation-concept}
To answer which problem difficulties can be troubleshot and at what success rate, the system is evaluated
against different fault scenarios. Each scenario injects a specific, known fault into
the network (for example a downed interface, a missing VLAN on a trunk, or a silently dropping ACL) and is
assigned a \emph{difficulty level}. The difficulty level conceptually captures how much correlation across
domains (topology, live state, history, syslog) and how many steps are required to localise the
fault.

\subsection{Use Case: Automatic Syslog Investigation}
\label{sec:autonomous-syslog-usecase}
As mentioned in \cref{sec:concepts-scope}, this use case is a separate, exploratory part of the project. Its
purpose is to answer whether an autonomous, event-driven investigation is possible at all and how it
can be integrated into the network operator's workflow. It
builds on the autonomous investigation orchestrator introduced in \cref{sec:agent-roles}. 

\paragraph{Autonomous reaction to syslog events}
The first question is whether the system can react to the network on its own. Instead of waiting for a human
to describe a symptom, the system observes the incoming syslog events and, when a message matches the configured pattern, an automatic investigation is launched. The autonomous investigation
orchestrator then follows the same pattern as the user-facing orchestrator with the exception of not having access to the configuration agent.
It is also designed so investigations cannot be opened recursively. The result is a self-contained initial report produced from a syslog event without any human
involvement.

\paragraph{Handover without duplicating work}
The second question concerns what happens after an autonomous investigation has run. Such an
autonomous report may be incomplete and need further investigation by a human (network operator).
The operator must therefore be able to take over and continue troubleshooting from the point the
autonomous investigation reached, without repeating the work it already did. The concept addresses
this by keeping the autonomous investigation's findings as reusable context (with a unique ID). When
the operator resumes the case, this context is fed back into the same investigation orchestrator that
produced it, so the case continues from its existing state instead of starting from scratch. How this
handover is realised concretely is described in \cref{sec:implementation}.
