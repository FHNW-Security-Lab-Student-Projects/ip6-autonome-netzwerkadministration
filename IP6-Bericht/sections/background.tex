\section{Background}
\label{sec:background}
This section gives the necessary background information about the technologies used in this work.

\subsection{Agents and AI Agents}
\label{sec:Agent_and_AI_Agents}
This subsection first defines the traditional term \emph{Agent} and then the newer \emph{AI Agent}.

\paragraph{Agent}
From a very basic perspective, an agent is an entity which is able to produce some effect or make changes in its
environment \parencite{CASTELFRANCHI1998157}.

\paragraph{AI Agent}
With the rise of generative AI a new term \enquote{AI Agent} has emerged.
An AI Agent is a piece of software that works towards a goal it has been given.
It takes in information from its environment (structured or not), reasons about what it sees and then
acts to get closer to that goal. A traditional agent executes a predetermined, deterministic
sequence of steps, whereas an AI agent responds to what it observes while running,
adjusting its behaviour and the results it produces as the situation changes. At its core, the decisions of such an
agent are made by an LLM (see \Cref{sec:LLMs}) \parencite{Sapkota_2026}.


\subsection{Large Language Models (LLMs)}
\label{sec:LLMs}
An LLM is a statistical model that predicts the likelihood of the next token in
a sequence of text. Trained on very large text corpora, largely taken from the
public internet, it learns to produce plausible continuations for a given input
prompt \parencite{douglas2023largelanguagemodels}. Nowadays most of the \enquote{AI Agents} are based on LLMs.


\subsection{Tokens, Context Windows and Cost}
\label{sec:tokens-context-cost}
LLMs do not operate on text (words and characters) directly. Text has to first go through a \emph{tokenizer} that breaks it into pieces called \emph{tokens}
which can be words, sub-words or even just single characters. The goal of a \emph{tokenizer} is to return an efficient set of tokens to represent a text dataset \parencite{alammar2024hands}.

Each model can only process a limited number of tokens at once. This upper bound is referred to as the
\emph{context window} and covers the prompt, any provided tools, the conversation history and the generated
response. Beyond being a hard limit, longer contexts also degrade the quality of the model's output:
\textcite{liu-etal-2024-lost} show that models use information most reliably when it appears at the beginning or the
end of the context and perform noticeably worse when relevant information is located in the middle, a
phenomenon known as \enquote{lost in the middle}. The degradation also depends on \emph{how much} context
surrounds the relevant information, not only on \emph{where} it sits: \textcite{hong2025context} evaluate a
range of state-of-the-art models on deliberately simple tasks and find that performance declines as the input grows longer, even when the task itself does not become harder. These two properties, the finite context window and the
degradation over long contexts, are a central motivation for distributing work across several specialised
agents rather than handling everything in a single, ever-growing context (see \Cref{sec:multi-agent}).


\subsection{Multi-Agent (AI) Systems}
\label{sec:multi-agent}
A multi-agent (AI) system (MAS) is a system composed of multiple interacting agents.
By combining the capabilities of its agents, such a system can address problems that a single agent or one monolithic system could not handle on its own \parencite{tran2025multiagentcollaborationmechanismssurvey}.

With the rise of LLM-based agents (AI agents) (see \Cref{sec:LLMs}), this idea has been transferred to systems in which
the individual agents are driven by LLMs. The survey by \textcite{tran2025multiagentcollaborationmechanismssurvey} describes how
multiple LLM agents collaborate through different coordination structures. The structure and
collaboration strategy chosen for this work are described in \Cref{sec:concepts}.




\subsection{Function Calling}
\label{sec:func-calling}
LLMs have great generative capabilities but they lack the ability to perform any task beyond generating a response.
This means LLMs are not able to retrieve any external information in real time.
Everything the model knows comes from its static training data, so an answer can sound convincing
while actually being wrong or simply out of date, a behaviour commonly called hallucination \parencite{Qu_2025}.
To address this limitation a paradigm named \enquote{Function Calling} has been developed.
It mitigates these problems by giving LLMs the ability to interact with external systems by invoking predefined blocks of code (functions), so that answers can be grounded in fresh, retrieved information instead of training data alone \parencite{wang2026FunctionCalling}.

\subsubsection{Function Calling Process Example Using the OpenAI API}
\Cref{fig:function-calling-procedure} illustrates the function calling principle using the OpenAI function calling API as an example. The function calling API is an optional part of the new \emph{Responses API} or the older \emph{Chat Completions API} \parencite{openai_responses_create,openai_function_calling}.

\begin{enumerate}
    \setlength{\itemsep}{8pt}
    \item The prompt message and all the tool definitions are sent to the model.
    \item Based on the provided prompt and tools the model decides to call some function, providing the necessary arguments (in this example \enquote{paris}).
    \item The function chosen by the model is executed.
    \item All prior messages together with the result (output) of the function execution are sent back to the model.
    \item Based on all the messages the model gives back a final response \parencite{openai_function_calling}.
\end{enumerate}

\subsection{Agent Loop and Agent Harness}
\label{sec:agent-loop}
Function calling (see \Cref{sec:func-calling}) explains how a model can request the execution of external code, but it does not
explain how an agent works on a task over multiple steps. Two concepts are needed for this. The \emph{agent loop}
describes the repeated cycle of reasoning, acting and observing that an agent goes through until a task is finished.
The \emph{agent harness} is the software around the model that actually runs this cycle. This subsection introduces
both, starting with the loop itself and then with the harness that drives it.

\subsubsection{Agent Loop}
Function calling (see \Cref{sec:func-calling}) describes a \emph{single} exchange in which the model receives a function, requests a
function execution and receives its result. On its own, this does not yet make a system agentic. The model still needs to be
invoked repeatedly, decide when another tool call is necessary, and recognise when the task is complete. This
repetition is captured by the term \emph{agent loop}, the core control cycle of an AI agent. The model receives the current
context, decides on an action (either calling a tool or producing a final answer), the chosen tool is executed, its
result is appended to the context, and the cycle repeats until the model returns a final answer or a stop condition is
reached \parencite{yao2023reactsynergizingreasoningacting,anthropic_effective_agents,strands_agent_loop}. These steps of reasoning and acting were introduced
as the \emph{ReAct} pattern by \textcite{yao2023reactsynergizingreasoningacting}. The agent loop is what turns isolated
function calls into the adaptive, goal-oriented behaviour of an AI agent as introduced in
\Cref{sec:Agent_and_AI_Agents}.

\Cref{fig:agent-loop} shows this cycle: an initial input and context enter the loop, the model reasons and selects a
tool, the tool is executed and its result is fed back for the next round of reasoning, and the loop repeats until the
model produces a final response.

\subsubsection{Agent Harness}
An LLM by itself cannot run this loop (the agent loop), as it only predicts a single continuation for a given input
(see \Cref{sec:func-calling}). The loop, the dispatching of tool calls, the accumulation of the message history and the
evaluation of stop conditions all have to be implemented by the surrounding software. This runtime software is
commonly referred to as the \emph{agent harness}: everything that is built around the model so that it can actually
work on a task instead of just answering a single prompt, often summarised as \emph{Agent = Model + Harness}
\parencite{databricks_ai_harness,langchain_agent_harness}. The harness is the engine that drives the agent loop (the core) and manages the
things around it. It forwards the conversation and the available tool definitions to the model, executes the tool
calls the model requests and maintains the message history across iterations. In practice a
harness is usually provided by an \emph{agent framework} with APIs to modify and extend its functionality. The concrete framework used in this work is described in
\Cref{sec:implementation}.

\Cref{fig:agent-harness} illustrates this relationship: the model sits at the centre and only reasons and decides,
while everything around it, the context injection, control, action (tool calls), observation and persistence, is
provided by the surrounding harness.

\subsection{Model Context Protocol (MCP)}
\label{sec:mcp}
The Model Context Protocol (MCP) is an open standard that specifies how AI applications
communicate with external systems \parencite{mcp_intro}. Through this protocol, an AI application
(for example a chat assistant) gains structured access to the outside world: it can read from data
sources such as databases or local files, and it can invoke executable tools.

The core problem MCP addresses is the fragmentation of AI integrations. Before MCP, hooking an AI
application up to a new data source meant writing yet another one-off integration, an approach that
quickly stops scaling as the number of connected systems grows \parencite{mcp_anthropic}. This is commonly framed as the $N \times M$
integration problem \parencite{mcp_nxm}. Without a common standard, connecting $N$ AI
applications to $M$ external systems (data sources and tools) requires a custom
integration for every AI application--external system pair, resulting in up to $N \times M$ separate
integrations that must each be built and maintained individually. MCP replaces this with a
single shared protocol. Every AI application implements the MCP client side once, and every
external system is exposed through an MCP server once. This reduces the integration effort
from a multiplicative $N \times M$ to an additive $N + M$ \parencite{mcp_nxm}.

As illustrated in \Cref{fig:mcp_architecture-overview}, MCP functions similarly to a
\enquote{USB-C port for AI applications} \parencite{mcp_intro}, one standard interface
through which an AI application can reach many different external systems.
