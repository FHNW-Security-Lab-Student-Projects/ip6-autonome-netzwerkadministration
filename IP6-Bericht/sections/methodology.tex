\section{Methodology}
\label{sec:methodology}
The system designed in \Cref{sec:concepts} is evaluated experimentally.
Where \Cref{sec:evaluation-concept} defined what a scenario and a difficulty level are, the
following describes how the experiments are run.

\subsection{Experimental Environment}
\label{sec:experiment-environment}
All experiments are run against a virtual network using \emph{containerlab} \parencite{containerlab}, so that the agents interact
with real device behaviour. The lab consists of Nokia SR Linux \parencite{srlinux} nodes with a predefined configuration and topology in which the test clients can reach each other
(\Cref{fig:testlab-topology}). This means the baseline is a fully functional network.

The topology contains four SR Linux nodes and four Linux clients. On one side, switch1
connects client1 (VLAN 10, 192.168.1.0/24) and client2 (VLAN 20, 192.168.10.0/24) and
carries both VLANs over a trunk to router1, which acts as their gateway. On the other side,
switch2 connects client3 and client4, which share VLAN 30 (10.10.10.0/24) with router2 as
their gateway. router1 (AS 65001) and router2 (AS 65002) exchange the client prefixes over
an eBGP session on the link between them. All devices send their syslog messages to a
central log store (see \Cref{sec:impl-tools}).

\subsection{Fault Scenarios and Difficulty Levels}
\label{sec:scenarios-difficulty}
The system is evaluated against a set of fault scenarios. Each scenario is packaged as a
folder. Its setup script injects exactly one known fault into the healthy baseline configuration (topology).
A scenario consists of:

\begin{itemize}
    \item \texttt{setup.sh}: Injects the fault before the queries are sent.
    \item \texttt{teardown.sh}: Restores the baseline after the experiment is done.
    \item \texttt{queries.txt}: The open-ended troubleshooting prompt given to the
          orchestrator (for example \enquote{investigate the root cause}), giving no hint about where to look.
    \item \texttt{ground\_truth.yaml}: A description of the true fault (root cause), used
          as the reference during manual evaluation (\Cref{sec:evaluation-procedure}).
\end{itemize}

\subsubsection{Difficulty Criteria}
\label{sec:difficulty-criteria}
Difficulty is defined by how far an agent has to go from the obvious first check to reach the
root cause. A fault being visible in syslog does not by itself make a fault easy. Three properties determine
the difficulty: (1) whether the obvious signal tells the truth or is misleading (for example a link that is up
while BGP is down), (2) how many devices or layers lie between where the symptom shows up and
where the fault actually sits and (3) how many signals must be correlated (a single show
command versus comparing two route tables or varying a packet size).

\subsubsection{Scenario Descriptions}
\label{sec:scenario-descriptions}
The following paragraphs describe each scenario in \Cref{tab:scenarios}: the fault that
\texttt{setup.sh} injects and why the scenario sits in its tier according to the criteria of
\Cref{sec:difficulty-criteria}.

\paragraph{Baseline}
\texttt{basic-client-communication} injects no fault. The network is healthy and the query asks
the agent system if client1, client2 and client3 can reach each other. The scenario checks that the system reports full
reachability and does not invent a fault that is not there. This is a check against hallucinated
faults.

\paragraph{Easy tier}
In the easy scenarios the fault sits exactly where the symptom points and the obvious signal is
the truth. A single \texttt{show} command on the right device reveals it, and the event is logged.

\begin{description}
    \item[\texttt{intf-down}] The interface connecting router1 to router2 is
          administratively disabled. The operational state goes down and the event appears in
          syslog, so one interface check on router1 reveals the fault. 
    \item[\texttt{client3-port-down}] The access port on switch2 towards
          client3 is administratively disabled.
          The down state is visible in a single interface check and in syslog. 
    \item[\texttt{switch1-uplink-down}] The trunk uplink from switch1 to router1
          is administratively disabled. The operational state goes down and the event appears in
          syslog, so one interface check on switch1 or router1 reveals the fault.
\end{description}

\paragraph{Medium tier}
In the medium scenarios the obvious signal is misleading. The fault sits one step away from
it, so the agent has to look one layer deeper.

\begin{description}
    \item[\texttt{missing-export-policy}] The eBGP export policy on router1 is removed.
          The BGP session remains established, but router1 no longer advertises
          its LAN prefixes, so router2 has no return route. The session state (BGP session) gives a false picture,
          checking it and stopping results in a miss. There is no syslog entry generated. The agent must inspect
          what is actually advertised and received (RIB-out/RIB-in), one layer below session state.
    \item[\texttt{missing-vlan-on-trunk}] The trunk uplink from switch1 towards
          router1 stops carrying the VLAN of client1, leaving that VLAN isolated from the network. The two obvious checks both pass, since the trunk port stays up (it still
          carries the other VLAN) and client1's access port is correctly configured.
          There is nothing logged to syslog.
    \item[\texttt{duplicate-ip-arp}] A second host claims client3's IP address while
          client3's switch port is briefly down, so the gateway (router2) relearns
          the address onto the wrong MAC and its ARP cache stays poisoned after
          client3 returns. A ping to the address still succeeds, because the second host
          answers, so a plain reachability check reports the network as fine. The giveaway is the
          mismatch between a pingable IP and a dead service on client3. The scenario is
          medium rather than hard because SR Linux names the conflict in syslog (a duplicate-address
          event listing both competing MACs).
\end{description}

\paragraph{Hard tier}
In the hard scenarios the configuration looks complete at every layer the agent normally checks
and nothing is logged. The fault hides where the agent has no reason to look until everything
else is ruled out. The main risk in this tier is that the agent concludes the network is
healthy.

\begin{description}
    \item[\texttt{acl-silent-drop}] An ingress ACL on router2 silently drops ICMP traffic
          from client1's subnet. Routing and BGP are fully healthy. The drop
          happens in the data plane, the agent has to think and check counters or inspect for a specific configuration.
          There is no syslog entry triggered when an ACL entry is hit.
    \item[\texttt{one-way-route-filter}] A BGP import policy on router1 rejects
          client3's prefix. The session is Established and router2 still
          learns client1's prefix, so every single-device check passes. The fault shows up only as an
          asymmetry between two route tables: the agent must compare router1's RIB
          against router2's and notice one prefix missing on one side.
    \item[\texttt{mtu-blackhole}] The IP MTU of router1's inter-router interface is
          lowered to 1280 bytes, creating a path-MTU blackhole. Small packets pass while large
          packets with the do-not-fragment flag are silently dropped. A normal ping
          succeeds, so the agent can wrongly conclude the network is fine. Finding the
          fault requires varying an input (trying with increasing packet sizes) and then
          inspecting the interface MTU.
\end{description}

A fourth, \emph{history-required} tier was originally planned: faults that are visible only
by comparing the current state against a recorded baseline, which would have made the
state-snapshot agent (\Cref{sec:agent-roles}) strictly necessary. Its intended use case,
\texttt{duplicate-ip-arp}, turned out to be visible in syslog on real SR Linux gear and was
therefore classified as medium instead. As a consequence, no scenario in the final catalogue
strictly requires the state-snapshot agent.

\subsection{Experiments}
\label{sec:experiments}
To study the effect of model capability and cost (the model-tier concept of
\Cref{sec:model-tier-concept}), every scenario is run against different models taken from the three price
tiers, with two models per tier:

\begin{itemize}
    \item \textbf{High:} \texttt{anthropic/claude-opus-4.8}, \texttt{openai/gpt-5.5}
    \item \textbf{Mid:} \texttt{z-ai/glm-5.2}, \texttt{qwen/qwen3.7-max}
    \item \textbf{Low:} \texttt{deepseek/deepseek-v3.2}, \texttt{mistralai/ministral-14b-2512}
\end{itemize}

The full matrix is the Cartesian product of all scenarios and all models, with each combination
repeated 5 times because of the non-deterministic nature of the models. The same model is used
across all agents. A wall-clock cap
of 600 seconds per run bounds the cost and duration of the 300-run matrix. Its influence on
the results is discussed in \Cref{sec:limitations}. A run that exceeds
the cap is recorded as \emph{did-not-finish} (DNF) while keeping the statistics of any sub-agents that
already completed.

\subsection{Experiment Execution}
\label{sec:experiment-execution}
The system under test is restricted to the read-only troubleshooting core of
\Cref{sec:architecture}: the user-facing orchestrator and its sub-agents. The configuration
agent and the syslog-triggered autonomous investigation (\Cref{sec:autonomous-syslog-usecase}) are
disabled for all runs (\Cref{sec:impl-interfaces}), since the experiments measure
the system's ability to find a fault. Applying a fix or detecting a fault unprompted are
separate capabilities outside the scope of this evaluation.

Each run follows the same procedure to guarantee a clean, comparable starting point.

\begin{enumerate}
    \item The lab is redeployed to a clean baseline and given time to settle (for example for BGP to come up).
    \item \texttt{setup.sh} injects the scenario's fault. 
    \item The orchestrator and all sub-agent tool servers are started, and the scenario's query is sent
          through the agent pipeline of \Cref{sec:architecture} (restricted as described above).
    \item Each turn of the run is appended to a structured log, together with a shared run identifier.
    \item \texttt{teardown.sh} restores the baseline in a finally block, so the next run is not
          contaminated. Additionally the lab is redeployed between every run.
\end{enumerate}

One property of this setup matters for interpreting the results. Each run gets a single, broad symptom
description and no follow-up. The
orchestrator receives this description and is explicitly instructed not to ask for
further information. From there the system (multi-agent network) has to work autonomously to a final answer. This
restriction exists because the matrix runs unattended. There is no human who could reply.
Real operation would be interactive, with a network operator able to guide the investigation.
\Cref{sec:limitations} discusses what this restriction likely costs in success rate. The experiments
measure the system in its most restricted mode of use.

Correctness for the experiments is scored separately (based on the final result of the orchestrator agent)
afterwards by a human (\Cref{sec:evaluation-procedure}).

\subsection{Recorded Metrics}
\label{sec:metrics}
For every run the following measurements are recorded, mapping directly onto the project's research
questions:

\begin{itemize}
    \item \textbf{Duration} per run, in two forms. The \emph{wall-clock duration} of the agent
          session is the time from submitting the query to the final answer, taken from the session's
          tracing spans so that the tooling around the run (lab redeployment, cost polling) is
          not counted. It is the basis for the time-saving question. The \emph{inference
          duration}, the summed model generation time across all agent runs as reported by
          OpenRouter per generation, compares model speed but is not a troubleshooting time.
          Agents running in parallel can make it exceed the wall clock.
    \item \textbf{Token usage} (prompt and completion) and \textbf{cost}, which is computed from the
          token counts and the model's advertised price per million tokens on OpenRouter. These are the basis for the cost question.
          Prompt caching is deliberately left out of this calculation. Not every provider applies
          server-side caching by default and where it exists it is often best-effort, so whether a
          run benefits would depend on which provider happened to serve it rather than on the model
          being tested. Pricing every token at the full list rate keeps the comparison fair across
          models, at the price of being a list-price estimate rather than the billed amount.
          In practice, real costs would tend to be lower where caching applies.
    \item \textbf{Completion status} (completed vs.\ DNF) and \textbf{invalid command count}, recorded
          when an agent issues a malformed device command, as an indicator of robustness.
    \item \textbf{Correctness verdict} per run, assigned manually (\Cref{sec:evaluation-procedure}), the
          basis for the success-rate question.
\end{itemize}

\subsection{Evaluation Procedure}
\label{sec:evaluation-procedure}
Correctness is scored manually. There is no LLM judge. Only the \textbf{final answer of each run} is
evaluated. For each run the
agent's final answer is compared to the scenario's root cause and classified as \emph{found} or
\emph{missed}. For the baseline scenario, correctly reporting the network
as healthy counts as \emph{found}.

The decision as to whether the root cause was correctly found is up to the human (author of this work) looking at the final answer of the agent (orchestrator).
